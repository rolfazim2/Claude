# Корпоративный таск-менеджер: Telegram-бот + веб-кабинет

> Предварительный продуктовый и технический дизайн.
> Аналог Asana по функциям, скорость и ощущение интерфейса — как Linear.
> Главный принцип: **Telegram заменяет мобильное приложение**, а сайт — это «толстый» рабочий кабинет.

---

## 0. Зафиксированные решения по скоупу (обновлено)

- **Single-tenant**: система только для одной компании. Никакого мультитенанта, переключения организаций и тарифов. Одна `Organization` зашита в конфиг.
- **Часовой пояс**: единый для всех — **Europe/Moscow**. Логики «TZ на пользователя» нет; все даты/напоминания/повторения считаются по МСК.
- **Дизайн/UI**: ориентир — **ClickUp** (структура и плотность), ощущение работы — Asana/ClickUp + скорость Linear.
- **Скоуп веб-сайта в MVP**:
  1. **Страница авторизации** (вход через Telegram).
  2. **Рабочая страница проектов/процессов** (список проектов/процессов + доска задач: канбан/список, карточка задачи).
  3. **Функциональная схема** — дерево функций компании; к функциям прикрепляются задачи, а уже потом назначается исполнитель.
- Всё остальное (карточки сотрудников, отдельный календарь, платёжный календарь, LLM-чат) — **за рамками MVP**, в бэклоге (см. §11).
- Telegram-бот остаётся полноценным каналом (создание задач, напоминания, выполнение с доказательством, комментарии) — он и есть «мобильное приложение».

### Роли и видимость (зафиксировано)
- **Главный администратор** (один — владелец): видит и делает всё.
- **Руководитель процесса**: видит **все задачи внутри своего процесса/проекта**, управляет ими.
- **Сотрудник (member)**: видит **только свои задачи** — даже если состоит в совместном проекте. Чужие задачи того же проекта ему не видны.
- **Участник задачи**: к любой задаче можно подключить доп. участника (watcher/соисполнитель) — он получает доступ к этой конкретной задаче.

### Функциональная схема — ядро модели (зафиксировано)
- Управление идёт **от функций, а не от людей**: администратор отвечает за функции и постановку задач в них, и лишь затем назначает задачу на сотрудника.
- Есть **дерево функций** компании. Задача **прикрепляется к функции**, после чего назначается исполнитель.
- Сотрудник может быть «привязан» к функции, но первичен узел функции, а не человек.

### Доказательство выполнения (зафиксировано)
- **Свободный формат**: скриншот / текст / ссылка (или их комбинация).
- Требуется **не всегда**, а только если администратор/руководитель включил флаг `proof_required` для задачи.
- Если флаг включён — **задача не может быть закрыта (перейти в `done`), пока не приложено доказательство**.
- Файлы хранятся **на нашем сервере** (self-hosted, см. §4).

## 1. Продуктовое видение

Единая система управления задачами компании с двумя равноценными точками входа:

- **Telegram-бот** — основной канал для исполнителей. Создание задач, напоминания, отметка о выполнении, комментарии, прикрепление доказательств — всё из чата. Авторизация на сайте тоже через Telegram.
- **Веб-кабинет** — в MVP это всего две страницы: вход и рабочая страница проектов/процессов (канбан/список + карточка задачи). Остальные модули — позже.

Данные общие: одна задача, созданная в боте, мгновенно видна на сайте и наоборот (real-time).

### Ключевое архитектурное решение
Бот и сайт — это **две «головы» к одному бэкенду**. Никакой логики «только в боте» или «только на сайте»: всё проходит через единый API/доменный слой.

## 3. Доменная модель (сущности)

```
Organization (компания — одна, зашита)
 ├── User (сотрудник; привязан к Telegram ID)
 ├── Function (узел ФУНКЦИОНАЛЬНОЙ схемы, дерево) ← ядро управления
 ├── Project / Process (проект ИЛИ процесс)
 │     ├── lead (руководитель процесса — видит все задачи внутри)
 │     └── Task
 │           ├── function_id  → к какой функции прикреплена задача
 │           ├── Assignee (User)            — назначается ПОСЛЕ выбора функции
 │           ├── Participant[] (доп. участники задачи)
 │           ├── Recurrence (правило повторения)
 │           ├── Reminder[] (за 1ч / за 1д / кастом)
 │           ├── Comment[]
 │           ├── Attachment[] / CompletionProof (скрин/текст/ссылка)
 │           └── ActivityLog[] (неизменяемый журнал)
 └── PaymentEvent (для платёжного календаря, бэклог)
```

### 3.1 User
- `telegram_id` (главный идентификатор для входа), `telegram_username`
- ФИО, должность, аватар
- `role`: `super_admin` (один, владелец) | `process_lead` | `member`
- `function_ids[]` — к каким функциям привязан (вторично; первична функция)
- статус (активен / в отпуске / уволен — без удаления)

### 3.1a Function (узел функциональной схемы) ← ключевая сущность
- `name`, `description`
- `parent_id` — дерево функций (через `ltree` / recursive CTE в Postgres)
- `responsible_user_id` (nullable) — кто сейчас исполняет функцию (может меняться, не влияя на функцию)
- К функции **прикрепляются задачи** (`Task.function_id`). Логика постановки: выбрал функцию → поставил задачу → назначил исполнителя.
- Удаление запрещено (архив), как и у задач.

### 3.2 Project / Process (проект или процесс)
- `type`: `project` | `process`
  - **project** — обычный набор задач с дедлайнами.
  - **process** — проект рутинных/повторяющихся операций (по умолчанию ежедневное повторение: «проверить кассу», «выгрузить отчёт»). Создаётся шаблон → воркер ежедневно «материализует» экземпляры задач.
- `lead_id` — **руководитель процесса** (видит все задачи внутри, управляет ими).
- участники, цвет, статус (активен/архив).

### 3.3 Task
- `title`, `description`
- `project_id`, **`function_id`** (к какой функции прикреплена)
- `assignee_id`, `creator_id`, `participant_ids[]`
- `priority`: `low` | `medium` | `high` | `critical` («супер-сложно»)
- `status`: `backlog` | `todo` | `in_progress` | `review` | `done` | `canceled`
- `due_at` (дата+время по МСК)
- `recurrence_id` (nullable)
- `is_deletable = false` — **удаление запрещено на уровне домена**. Доступны только: `done`, `canceled` (с обязательной причиной), `archive`. Любое действие пишется в `ActivityLog`.
- **`proof_required: bool`** — ставит администратор/руководитель. Если `true`, переход в `done` **блокируется**, пока не приложен `CompletionProof`.
- `completion_proof` — свободный формат: текст и/или ссылка и/или файл-скриншот.

### 3.3a Видимость задач (правила доступа)
- `super_admin` — видит все задачи.
- `process_lead` — видит все задачи **в своих процессах/проектах**.
- `member` — видит **только задачи, где он `assignee` или `participant`** (даже внутри общего проекта чужие задачи скрыты).
- Реализуется фильтрацией в сервисном слое (а не только на фронте) + проверкой на каждом API-эндпоинте.

### 3.4 Recurrence (движок повторений)
Правило в духе RRULE (iCalendar):
- `daily` / `weekly` / `monthly` / `quarterly` / `on_date(specific date)`
- `interval`, `by_weekday`, `by_monthday`, `time_of_day`, `until` / `count`
- Реализация: **шаблон задачи** + воркер, который заранее (например, на 30 дней вперёд) создаёт конкретные экземпляры. Это даёт корректный календарь и напоминания без «магии на лету».

### 3.5 Reminder
- `offset`: `-1h`, `-1d` (плюс кастомные в будущем)
- канал: Telegram (push на сайте/PWA — позже)
- статус: scheduled / sent / dismissed

### 3.6 Attachment / CompletionProof (доказательство выполнения)
- **Свободный формат**: `text` (комментарий), `link` (ссылка), `file` (скриншот/документ) — можно сразу несколько.
- В Telegram — прямо из чата (фото/файл/текст/ссылка); на сайте — drag&drop / вставка ссылки / текст.
- `kind`: `attachment` (обычное вложение) | `completion_proof` (доказательство закрытия).
- Бизнес-правило: если у задачи `proof_required = true`, переход в `done` запрещён без хотя бы одного `completion_proof`.
- Хранение — **на нашем сервере** (self-hosted MinIO или локальная папка за обратным прокси), без внешних облаков.

### 3.7 ActivityLog (журнал, неизменяемый)
Так реализуется «невозможность удалить»: ничего не пропадает, всё — append-only. Кто, что, когда изменил; смена статусов, исполнителя, комментарии.

## 4. Технологический стек («шустрый как Linear»)

Ощущение скорости Linear = **локальный кэш + оптимистичные обновления + real-time синхронизация**, а не «дёргать сервер на каждый клик».

### Frontend (Веб + мобильный)
- **React + TypeScript + Vite**
- **TanStack Query** + оптимистичные мутации (UI отвечает мгновенно, синхронизация — в фоне)
- **Zustand** для локального состояния
- **Tailwind CSS** + shadcn/ui — быстрый, аккуратный UI
- **Real-time**: WebSocket (см. бэкенд) → мгновенное появление чужих изменений
- **PWA** (offline-кэш, установка на телефон, push) → закрывает «мобильную версию»
- Виртуализация списков (react-virtual) для больших досок

### Backend
- **Node.js (NestJS) + TypeScript** — единый язык с фронтом, быстрый DX
  - *(альтернатива: Go/Fastify, если нужен максимум по латентности)*
- **PostgreSQL** — основная БД (надёжные транзакции, **дерево функциональной схемы** через `ltree`/recursive CTE)
- **Redis** — кэш, очереди, pub/sub для real-time
- **BullMQ** (на Redis) — отложенные напоминания и материализация повторяющихся задач
- **WebSocket-шлюз** (Socket.IO / native ws) — real-time апдейты на сайт
- **Хранилище файлов — на нашем сервере**: self-hosted **MinIO** (S3-совместимый, но локально) или файловая папка за обратным прокси. Без внешних облаков.

### Telegram-бот
- **grammY** (TS) или **aiogram** (Python) — webhook-режим
- Тот же бэкенд-API; бот — тонкий клиент над доменным слоем
- Inline-кнопки, deep links, file upload, mini-app (Telegram Web App) для сложных экранов

### LLM-чат
- Провайдер: Anthropic Claude (или совместимый), стриминг ответов
- Доступ к контексту задач через инструменты (function calling): «покажи мои просроченные», «создай задачу…», «кто перегружен»

### Инфраструктура
- Docker + docker-compose (dev), деплой — Fly.io / Railway / VPS + Caddy
- Миграции — Prisma / Drizzle
- Мониторинг — Sentry + простой uptime-чек

## 5. Авторизация через Telegram

Два сценария — оба официальные и безопасные:

1. **Telegram Login Widget** на сайте: пользователь жмёт «Войти через Telegram», подтверждает в приложении, сайт получает подписанные данные (проверяем HMAC по bot token). По `telegram_id` находим/создаём `User`.
2. **Из бота** (`/login`): бот присылает кнопку с одноразовой magic-link / кодом, по которому сайт логинит.

После входа — сессия через JWT (access + refresh) или httpOnly-cookie. Привязка `telegram_id` — это «единый аккаунт» для бота и сайта.

## 6. UX: экраны веб-кабинета

> UI-ориентир — **ClickUp / Asana**: левый сайдбар с иерархией, плотный список/канбан в центре, выезжающая карточка задачи справа. Плюс скорость и горячие клавиши Linear.

### MVP — три экрана

**A. Страница авторизации**
- Логотип, кнопка «Войти через Telegram» (Login Widget).
- После входа — редирект на рабочую страницу. Сессия в httpOnly-cookie.
- Ничего лишнего: один экран, один путь.

**B. Рабочая страница проектов/процессов** (главный экран, в стиле ClickUp)
- **Левый сайдбар**: список проектов и процессов (процесс помечен иконкой повторения), пункт «Мои задачи», пункт «Функциональная схема».
- **Центр**: доска задач выбранного проекта с переключателем вида:
  - **Канбан** — колонки по статусам (`backlog → todo → in_progress → review → done`), drag&drop, оптимистичный UI.
  - **Список** — плотная таблица, инлайн-редактирование, сортировки/фильтры (исполнитель, приоритет, срок, функция).
- **Видимость по ролям** (§3.3a): сотрудник видит на доске только свои задачи; руководитель процесса — все задачи процесса; главный админ — всё.
- **Быстрое создание** — строка вверху доски + `Cmd+K`. При создании: проект → **функция (из схемы)** → исполнитель → приоритет → срок → повтор → флаг «нужно доказательство».
- **Карточка задачи** (выезжает справа): описание, **функция**, исполнитель и участники, приоритет, срок+время, повторение, напоминания, комментарии, вложения и **доказательства выполнения** (текст/ссылка/скрин), журнал. Кнопки `Выполнить` / `Отменить` / `В архив` (удаления нет). Если `proof_required` — кнопка `Выполнить` неактивна, пока не приложено доказательство.

**C. Функциональная схема** (ядро управления)
- **Дерево функций** компании (раскрывающиеся узлы, drag&drop для переноса).
- У каждого узла: ответственный (опционально) и **список прикреплённых задач** с их статусами.
- Из узла можно сразу **поставить задачу в функцию** → затем назначить исполнителя.
- Это управленческий вид «от функций, а не от людей».

UX-принципы: клавиатурная навигация, command palette, оптимистичный UI, минимум модалок, тёмная тема, адаптив/PWA для телефона.

### Позже (бэклог, за рамками MVP)
- Отдельный «Календарь событий», карточка сотрудника, платёжный календарь, AI-чат. Доменная модель уже учитывает их, чтобы не переделывать БД.

## 7. UX: Telegram-бот (основные сценарии)

- `/start` → регистрация/привязка аккаунта.
- **Создать задачу**: текст или мастер из кнопок (проект → функция → исполнитель → приоритет → срок → повтор → нужно ли доказательство). Можно естественным языком — парсим через LLM.
- **Мои задачи**: список с инлайн-кнопками `✅ Выполнено` / `💬 Коммент` / `📎 Доказательство` / `⏰ Напомнить позже`. У сотрудника здесь только его задачи.
- **Напоминания**: бот сам пишет за 1 день и за 1 час до `due_at` (по МСК). Кнопки прямо в напоминании.
- **Доказательство выполнения**: пользователь присылает текст / ссылку / фото в ответ → крепится как `completion_proof`. Если `proof_required` — без него `✅ Выполнено` не сработает.
- **Комментарии**: ответом на сообщение задачи.
- **Назначение исполнителя**: при создании или через карточку задачи.
- Сложные экраны (канбан, календарь) — через **Telegram Mini App** (тот же React, внутри Telegram).

## 8. Платёжный календарь (модуль)

- Сущность `PaymentEvent`: контрагент, сумма, валюта, дата платежа, статус (запланирован/оплачен/просрочен), привязка к проекту/задаче.
- Может быть **повторяющимся** (тот же recurrence-движок): аренда раз в месяц, налоги раз в квартал.
- Напоминания о платежах в Telegram (за 1 день/1 час) — переиспользуем scheduler.
- Представление — календарь + список с суммами по периодам (план/факт).

---

## 9. Как реализуется «нельзя удалить»

- В домене нет операции `delete` для `Task`/`Project`/`PaymentEvent`.
- Вместо удаления: `cancel` (с обязательной причиной) или `archive`.
- Всё пишется в `ActivityLog` (append-only). Физическое удаление возможно только миграцией БД администратором — не из интерфейса.
- На уровне БД — мягкая блокировка (нет DELETE-эндпоинтов; права через RLS-подобную проверку в сервисном слое).

---

## 10. Real-time и скорость

- Любое изменение → запись в БД → событие в Redis pub/sub → рассылка по WebSocket подписчикам проекта/пользователя.
- Фронт применяет изменение **оптимистично** ещё до ответа сервера; при конфликте — мягкий откат.
- Бот получает те же события (для мгновенных уведомлений).

## 11. Дорожная карта (по этапам)

### MVP (single-tenant, TZ Europe/Moscow) — 3 экрана сайта + бот
- Auth через Telegram (страница авторизации), единый аккаунт бот↔сайт
- Роли и видимость: `super_admin` / `process_lead` / `member` + участники задач
- Задачи: создание/редактирование (без удаления), приоритеты, исполнитель, участники, срок+время
- **Функциональная схема** (дерево функций) + прикрепление задач к функциям
- Проекты и процессы, повторения (день/неделя/месяц/квартал/дата) по МСК
- Напоминания за 1ч/1д в Telegram
- Доказательства выполнения (текст/ссылка/скрин), блокировка закрытия при `proof_required`; комментарии
- Веб (ClickUp-стиль): **проекты/процессы** (канбан/список + карточка) + **функциональная схема** (+ адаптив/PWA), фильтр «Мои задачи»
- Хранилище файлов self-hosted (MinIO)
- Бот: создание, мои задачи, выполнение с доказательством, напоминания, комментарии
- Real-time синхронизация бот↔сайт

### v1.1 (бэклог)
- Отдельный «Календарь событий», Telegram Mini App для канбана

### v1.2 (бэклог)
- Карточка сотрудника со списком задач
- Платёжный календарь
- LLM-чат на сайте, аналитика загрузки

## 12. Открытые вопросы

### ✅ Решено
- **Масштаб** — single-tenant, только наша компания.
- **Часовые пояса** — единый Europe/Moscow.
- **UI** — стиль ClickUp / Asana.
- **Скоуп сайта в MVP** — авторизация + проекты/процессы + функциональная схема.
- **Роли** — `super_admin` (владелец) / `process_lead` (видит все задачи процесса) / `member` (видит только свои задачи) + подключаемые участники задач.
- **Функциональная схема** — управление от функций; задачи прикрепляются к функциям, затем назначается исполнитель.
- **Доказательство выполнения** — свободный формат (текст/ссылка/скрин); требуется по флагу от админа/руководителя; при включённом флаге закрытие задачи блокируется без доказательства.
- **Файлы** — на нашем сервере (self-hosted MinIO).

### Осталось уточнить (не блокирует старт)
1. **Процесс**: расписание строго ежедневное, или у процесса может быть любое (неделя/месяц/квартал)?
2. **Кто ставит задачи**: только `super_admin` и `process_lead`, или `member` тоже может создавать свои?
3. **Глубина функциональной схемы** на старте — примерный список функций верхнего уровня (чтобы засеять дерево).
