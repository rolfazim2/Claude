# opt-spb-agent

Автономный AI-агент разбора оптовых тегов магазина **opt-spb.ru** (OpenCart-Pro 2.3.0.2).
Заменяет ручную работу контент-менеджера: привязывает теги поставщиков к точным карточкам
товаров, создаёт новые карточки при отсутствии точного совпадения и выносит спорные случаи
на согласование владельцу — с требованием точности **≥ 95 %**.

Стек: **TypeScript + Playwright** (браузер) + **Claude API** (решающий слой матчинга).
Запуск: **GitHub Actions по расписанию** (cron) — «GitHub как сервер».

---

## Почему именно так (ключевой инсайт)

Главный задокументированный блокер проекта: программная привязка тега через `fetch`/`edit_tag`
возвращает пустой `HTTP 200` и **не сохраняется**; `$(sel).val(id).trigger('change')` тоже не
ставит value у AJAX-Select2. А **настоящий клик мышью** по варианту выпадающего списка (доверенное
browser-событие) — **сохраняется** (подтверждено для свежих строк, отчёт 28.05.2026).

Playwright диспатчит именно доверенные события. Поэтому агент не дёргает endpoint напрямую, а
воспроизводит ручной сценарий 1-в-1: открыть Select2 нужной строки → ввести запрос → дождаться
опций → **кликнуть точный вариант**. Это снимает блокер привязки. См. `src/browser/bind.ts`.

## Архитектура

```
src/
├── index.ts              оркестратор: вход → очередь снизу вверх → parse→search→decide→act → отчёт
├── config.ts             конфиг из ENV (режим, порог, бюджет времени)
├── state.ts              память между прогонами (уже вынесенные на review теги)
├── report.ts             markdown-отчёт прогона (рулбук 6.7)
├── knowledge/            БАЗА ЗНАНИЙ из «База проекта opt-spb.ru»
│   ├── rules.ts          рулбук как системный промпт для Claude (кэшируется)
│   ├── suppliers.ts      supplier_id → имя и тип по умолчанию
│   ├── filters.ts        известные ID фильтров/категорий/производителей
│   ├── countries.ts      флаги/слова → страна (фундаментальный параметр SKU)
│   └── colors.ts         цвета рус↔англ
├── matching/
│   ├── parse.ts          тег → структурированный TagConfig (модель/память/цвет/страна/тип/…)
│   ├── verify.ts         СТРОГАЯ 1:1 верификация (предохранитель против word-overlap)
│   └── decide.ts         Claude выносит вердикт: bind | create | review | skip
└── browser/
    ├── session.ts        вход в админку (form.submit(), токен из URL)
    ├── queue.ts          чтение «Не найденные теги» снизу вверх
    ├── search.ts         поиск кандидатов (catalog/import_tags/search)
    ├── bind.ts           ПРИВЯЗКА реальным кликом Select2  ← снимает блокер
    ├── create.ts         создание карточки (категория/фильтры/картинка) по чеклисту
    ├── image.ts          загрузка в filemanager / переиспользование изображения
    └── yandex.ts         поиск картинки в Яндексе + vision-проверка цвета/модели
```

### Конвейер решения по одному тегу
1. **parse** — извлечь модель, чип/поколение, RAM/ROM, цвет (рус+англ), страну (флаг/слово),
   тип (с учётом дефолта поставщика), связь, NFC, диагональ, партномер.
2. **search** — собрать кандидатов несколькими короткими запросами (AND по подстрокам,
   без бренд-слов, память через «/»).
3. **verify** — детерминированный предохранитель отсекает кандидатов с конфликтом по памяти,
   чипу, цвету, **стране (включая отсутствие)**, типу, связи. Это НЕ скоринг похожести.
4. **decide (двухступенчато, экономия токенов):**
   - *Fast-path без LLM (0 токенов):* ровно один кандидат прошёл строгую верификацию и тег
     информативен (≥2 сигнала) → bind; ноль кандидатов и полный парс → create, название
     строит детерминированный конструктор по паттернам сайта (`matching/title.ts`).
   - *LLM-арбитраж (Claude):* только неоднозначные случаи — несколько кандидатов, неполный
     парс. Рулбук кэшируется (prompt caching), промпт ужат, расход токенов пишется в отчёт.
5. **act** — `bind` (реальный клик), либо `create` (+ привязка к новой карточке), либо `review`.

### Работа «из коробки» и расход токенов
- **Без `ANTHROPIC_API_KEY` агент полностью работоспособен**: однозначные случаи решает
  детерминированно, спорные честно выносит в review. Обязательны только логин и пароль.
- С ключом добавляются арбитраж спорных тегов и vision-проверка картинок Яндекса
  (до 4 кандидатов на тег, остановка на первом подтверждённом).
- Каждый отчёт прогона содержит строку `LLM: N вызовов, токены in/out`, чтобы расход был виден.

## Режимы (`AGENT_MODE`)

| Режим | Поведение |
|---|---|
| `full` | Привязка матчей ≥95% **и** создание карточек (картинка обязательна). Спорное → отчёт. |
| `safe` | Только привязка матчей ≥95%. Создание и спорное → отчёт на согласование. |
| `dry-run` | Ничего не меняет на сайте: парсит, ищет, считает уверенность, пишет отчёт-план. |

Во всех режимах действует правило ≥95%: при любом сомнении — `review`, действие не выполняется
(рулбук 3, 6.6). Создание карточки откладывается на ревью, если нет аналога для категории/
производителя, неизвестен нужный фильтр или **нет точной картинки нужного цвета** (правило 6.4).

### Источник картинок (`AGENT_IMAGE_SOURCE`)

| Значение | Поведение |
|---|---|
| `analog` | Только переиспользовать фото аналога **того же цвета** (без внешних источников). |
| `yandex` | Только Яндекс.Картинки. |
| `analog+yandex` | Сначала аналог, затем Яндекс (по умолчанию). |

Яндекс-пайплайн (`src/browser/yandex.ts`) учитывает узкое место из базы (брали «White вместо
Pink Gold»): берёт превью с CORS-открытого CDN `avatars.mds.yandex.net`, отсекает мелкие тумбы и
**каждого кандидата проверяет Claude vision** — точная ли это модель и точный ли цвет, без
коллажа/ватермарки. Картинка ставится только при подтверждении (conf ≥ 0.9); иначе тег → review.
Если Яндекс отдаёт капчу/блокирует IP раннера — агент не падает, а отправляет карточку на ревью.

## Настройка

### 1. Секреты репозитория (Settings → Secrets and variables → Actions → Secrets)
| Secret | Значение |
|---|---|
| `OPT_SPB_LOGIN` | логин админки (`magazim`) |
| `OPT_SPB_PASSWORD` | пароль админки |
| `ANTHROPIC_API_KEY` | ключ Claude API |

> ⚠️ Пароль и ключ **никогда** не коммитятся в репозиторий — только в Secrets.

### 2. (необязательно) Переменные (Variables) для тонкой настройки
`OPT_SPB_BASE_URL`, `AGENT_MODEL`, `AGENT_MODE`, `AGENT_CONFIDENCE_THRESHOLD`,
`AGENT_TIME_BUDGET_MIN`, `AGENT_MAX_TAGS`.

### 3. Запуск
- **Вручную:** вкладка **Actions → opt-spb-tag-agent → Run workflow** (можно выбрать режим и
  поставить `max_tags=5` для первой обкатки).
- **По расписанию:** cron `5 * * * *`. ⚠️ GitHub запускает `schedule` **только из ветки по
  умолчанию**. Чтобы почасовой автозапуск заработал, влейте агент в default-ветку (`main`).
  До этого пользуйтесь ручным запуском.

Отчёт каждого прогона:
- сохраняется в `reports/cron_run_YYYY-MM-DD_HH.md` и **коммитится обратно в ветку**;
- дополнительно выкладывается как artifact прогона.

## Локальный запуск (для отладки)

```bash
cd opt-spb-agent
npm install
cp .env.example .env   # впишите логин/пароль/ключ
npm run agent          # AGENT_HEADLESS=false в .env — чтобы видеть браузер
```

## Разработка

```bash
npm run typecheck      # строгая проверка типов
npm test               # юнит-тесты парсера и строгой верификации (без сети/браузера)
```

Тесты покрывают разобранные кейсы и инциденты из базы: M5≠M4, тег без страны ≠ карточка со
страной, Denim≠Синий, распознавание секционных заголовков, дефолтные типы поставщиков и др.

## Рекомендуемый порядок ввода в эксплуатацию
1. `dry-run` вручную с `max_tags=20` — посмотреть, как агент классифицирует свежие теги.
2. `full` вручную с `max_tags=5` — проверить реальные привязку/создание на нескольких тегах.
3. Расширять лимит; затем влить в default-ветку для почасового cron.

## Что осталось открытым (из базы проекта)
- Качество Яндекс-рендеров на масштабе (vision-проверка отсекает брак, но часть карточек уйдёт
  в review, если чистого фото нужного цвета нет) — при необходимости добавить CDN производителей.
- Поведение Яндекса на IP раннеров GitHub (возможна капча) — проверить на обкатке.
- Policy для поставщика 18 (формат «• A37 8/128 Charcoal») и секционных заголовков.
- Расширение справочника `filters.ts` новыми значениями фильтров по мере встречи моделей 2025–2026.
